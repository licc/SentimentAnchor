# 更新记录

## 2026-10-25 · 性能：thsapi 读表裁剪 + 首页停止每秒重渲染

### thsapi：读表前裁掉底部空白

表格整块送进 OCR 时，空白区域要吃掉 80%~90% 的算力。现在按"文字"阈值（灰度 150）找最后一行内容再裁：
**浅灰网格线不算内容**——用 245 阈值时包围盒会被边框撑满（实测占比 100%），裁不掉任何东西。

| 接口 | 优化前 | 优化后 |
| --- | --- | --- |
| `/api/v1/orders`（空表） | 6.3–8.0 s | **3.8–3.9 s**（-43%） |
| `/api/v1/trades`（空表） | 3.5 s | 3.5 s |
| `/api/v1/portfolio`（1 行 + 汇总行） | 4.7–4.8 s | 4.8 s（**无收益**：汇总行在最底部，裁不掉） |

- 只裁底部、保留整幅宽度：列检测依赖竖向网格线，横向裁切会让列边界失效。
- `OcrTable` 新增 `origin`：单元格补读要换算回屏幕坐标，裁剪偏移必须加回去。
- 裁剪后表头仍正确解析（实测 `委托时间/证券代码/…`、`成交时间/…`），空表数据行为 0。

**portfolio 的下一步（未做）**：底部有"汇总"行，裁剪无效。可选：
① 先 OCR 左侧窄条定位行区间再裁；② 把 `cache_ttl_s` 从 3 调到 8–10（前端本就 10 秒轮询，代价是最多旧 10 秒）。

### 前端：把"每秒变化"下沉，App 不再整棵树重渲染

原来 `useMarketData` 每秒 `setState`（`now` / `countdown`），导致 **App 整棵树每秒重渲染一次**——
包含情绪曲线、涨停池、交易台这类大 SVG / 长列表，页面开着不动也持续吃 CPU。

- 新增 `src/components/LiveBits.tsx`：`LiveClock` / `NowText`（各自 1 秒定时器）、
  `RefreshRing`（按"收到帧的本地时刻"自行倒计时）。
- `useMarketData` 不再持有 `now` / `countdown`，只暴露 `appliedAt`（每帧变化，约 10 秒一次）；
  兜底轮询检查从 1 秒放宽到 2 秒，且不再触发渲染。
- `TopBar` / `App` / `EtfPage` 改用这些小组件。

效果：秒级渲染从"整棵树 × 3600 次/小时"降为"两个小节点"；整树只在快照到达时更新（10 秒一次）。

## 2026-10-25 · 接口性能优化（带宽 / 载荷）

先量化再动手。优化前实测：

| 接口 | 原始体积 | 备注 |
| --- | --- | --- |
| `GET /api/snapshot` | 78 KB | SSE 每 10 秒推一帧，未压缩 |
| `GET /api/sentiment/history?days=30` | 200 KB | 含每日 243 点分钟序列，而前端只用日级 4 个字段 |
| 服务端压缩 | **完全没有** | 响应只有 `Content-Type: application/json` |

改动：

1. **启用 gzip**（`compression` 中间件）：
   - `/api/snapshot` 78 KB → **19.8 KB**（-75%）
   - `/api/sentiment/history?days=30` 200 KB → **22.6 KB**（-89%）
   - `/api/system/health` 2.2 KB → 1.1 KB
   - **SSE 显式排除**：`/api/stream` 不带 `Content-Encoding`；否则中间件会缓冲事件流，页面会"不刷新"（已实测确认）。
2. **情绪归档支持 `points=0`**：多日趋势只需要 日期/收盘/最高/最低，前端改请求精简版。
   30 日：200 KB → **3.1 KB**（gzip 后 **580 B**，约 -98%）。

**一个被证伪的优化**：曾把表格 OCR 放大倍数从 1.6 降到 1.2，看似"6.4s→3.6s"，
但那是 **RapidOCR 首次加载模型** 的噪声；稳态下两者都是 ~3.6s。
因此保留 1.6（精度余量更大），只加 `THSAPI_OCR_SCALE` 环境变量便于实验。

**仍然存在的热点（未改，需要权衡）**

| 位置 | 现状 | 可选做法 |
| --- | --- | --- |
| thsapi `/api/v1/orders` | ~8 s | 疑似读两次表格，需分段确认 |
| thsapi `/api/v1/portfolio` | ~5 s | 其中表格 OCR ~3.6 s；可先裁掉空白区域再识别（预计 -50% 以上） |
| thsapi 查询缓存 | `cache_ttl_s: 3` | 前端每 10 s 轮询，调到 8–10 s 命中率明显提高，代价是最多旧 10 s |
| 后端 `/api/system/health` | ~5 s | 等 thsapi 持仓；可复用 `ETF_STATUS_TTL_MS` 或并行取报价 |
| SSE 帧 | 78 KB/帧（未压缩） | 帧内 gzip 或增量下发，改动较大 |

## 2026-10-25 · 下单链路的三个漏洞修复

现象：调用下单接口返回 400，耗时 15–19 秒，返回「当前不在交易时段（委托单已按要求填好，但未提交）」，
同时日志里有 `价格/数量回读不一致: 期望 1.85 实际 2.244`。

定位结论（逐条验证过）：

1. **休市拦截是设计行为**。周日 `is_trading_time()` 为假，`safety.allow_out_of_hours` 默认 false，
   而 `check_submit_window()` 被刻意放在"填单之后、提交之前"，所以每次都要先操作界面 10 多秒才拒绝。
2. **价格偏离校验可被调用方绕过**。原逻辑优先用调用方传入的 `ref_price`，调用方把 `price` 和 `ref_price`
   填成同一个值，偏离就是 0%，校验形同虚设。
3. **价格越界后仍继续执行**。示例价 1.85 低于 513100 当日跌停价（现价 2.243 → 跌停约 2.036），
   客户端把输入夹回 2.244，回读不一致只打了 warning 就继续走完流程。
4. 另外发现 **买入页根本没有「现价」控件**（只有 证券代码/证券名称/买入价格/可买(股)/可用/买入数量），
   所以 `prepare()` 读到的 `last_price` 恒为 0，基于页面现价的校验天然失效。

修复：

- `guard.validate_context`：偏离校验改为**以页面现价为准**，读不到时才退回 `ref_price`；不再接受调用方自证。
- `etf-broker.placeEtfOrder`：新增 `refPrice`，手动下单路径由后端把**行情里的真实报价**作为 `ref_price` 传给适配器。
- `ths.gui._set_field`：写入后回读不一致 → 重试一次，仍不一致则抛 `order_rejected` **中止**，
  消息里给出期望值/界面值并提示「价格超出涨跌停被客户端夹住」。绝不按界面上的价格继续提交。
- `webdocs` 下单示例：价格由过期的 1.85 改为占位 2.2，去掉 `ref_price` 并在注释里写明"示例价不要照抄"。

验证：`pytest` 22 passed；直接调 thsapi 传 1.85 现已明确返回
`order_rejected: 委托价格写入后回读不一致：期望 1.85，界面显示 2.244；已中止，未提交`。

另注：**交易台下单在 dry_run 下会被后端 409 拦住**（`broker.mode !== 'live'`），
所以之前那些 400 来自直接调用 8888 的接口（例如文档页「试调用」），不是 App 的交易台。

## 2026-10-25 · 30 日历史回填 + SQLite 存储

### 能不能算：能，而且是精确复算

- 选股宝广度接口支持 `date=YYYY-MM-DD`，能返回**任一交易日**完整的 243 个分钟点；
- 温度公式（`analysis.buildChart`）只依赖广度四元组（涨跌家数、涨跌停数），
  不依赖指数/涨停池这些"只有当日才有"的数据 —— 所以历史是**同一口径复算**，不是估算或代理指标。

### 存储改为 SQLite

- 新增 `data/sentiment.db`（表 `sentiment_daily`：日期、收盘温度、最高、最低、分钟序列、更新时间）。
  用 Node 24 内置的 `node:sqlite`，**零新增依赖、无需编译**。
- 当日数据仍由行情 tick 每分钟覆盖写；旧的 `data/history/sentiment/*.json` 会在首次启动时一次性导入后不再使用。
- 选择数据库而不是 JSON 文件的理由：需要按日期范围查询与按日 upsert，且归档会长期增长。

### 回填

- 新增 `POST /api/sentiment/backfill?days=30`（`&force=1` 重新校验已有日期）。
- 服务启动时若归档不足 30 天，会在后台静默回填，串行 + 150ms 限速，不阻塞启动。
- 实测：29 个交易日约 15 秒补齐，每日本身 243 个点，日线视图可正常切换 7/14/30 日。

### 多日视图补上「日内振幅」

- 每天除收盘点外，加一条**竖线表示当日最高–最低**（类似 K 线的影线/下引线），
  否则只看收盘会把剧烈的日内摆动抹平：例如 **10-23 收盘 79，但 10:20 曾低至 6**（当日振幅 73）。
- 悬浮某一天时该竖线高亮，tooltip 仍显示收盘 / 当日最高 / 当日最低。
- 近 7 日实测振幅：10-15 25、10-16 30、10-19 30、10-20 42、10-21 27、10-22 38、10-23 73。

### 踩坑：上游对非交易日会静默回退

- 请求 `date=2026-10-01`（国庆假期）时，接口返回的是 **2026-09-30** 的完整数据，
  如果不校验，同一交易日会被重复写进多个日期。
- 现在回填会核对返回数据自身的日期（首点与末点都必须等于请求日期），不匹配即丢弃，
  并顺手删除之前误写入的脏行。清理后实测库内 34 个交易日，无周末、无节假日。

## 2026-10-25 · 局域网访问与 OCR 识别修复

### 前端

- **SSE 断线自建重连**。`EventSource` 只在"网络层断开"时自动重连；若服务端（或开发代理）返回的是
  一个合法的 HTTP 非 200（例如后端重启瞬间代理报 `502`/`ECONNREFUSED`），按规范客户端会**永久放弃**，
  页面从此收不到快照、停在旧数据上。现在改为 `onerror` 里主动 `close()` 并重建连接，
  退避 2s → 4s → 8s → 16s（上限 30s）。
- **倒计时改为纯本地计时**。原实现是 `nextRefreshAt − 客户端本地时钟`，远程设备（手机/另一台电脑）
  时钟只要偏差几秒，倒计时就恒为 0，顶部环形进度条看起来"不转"，误以为没有刷新。
  现以"收到上一帧的本地时刻"为基准推算，与设备时钟无关。
- **兜底轮询收紧**。连续 12 秒（原 22 秒）收不到推流时自动改走 `GET /api/snapshot`，即使 SSE 被中间层掐断，
  数据也不会僵住。
- **局域网可访问**。`vite` 监听改为 `0.0.0.0`；`server.watch` 排除 `thsapi/`（其 `.venv` 含上万个文件，
  纳入监听会拖垮 dev server）。

### 后端

- `GET /api/health` 新增 `sseClients` 字段（当前挂着 `/api/stream` 的浏览器数量），
  `/api/stream` 增加接入/断开日志。排查"远程页面不刷新"时先看这两个信号：
  `sseClients` 为 0 说明页面根本没订阅上，而不是数据没变。
- `HOST` 支持 `0.0.0.0`；非回环且未设置 `APP_TOKEN` 时会打印安全提示（原有逻辑，本次确认可用）。

### thsapi 适配器（同花顺 GUI 通道）

- **新增 RapidOCR 主引擎**：`thsapi/gui/ocr_rapid.py`，使用 RapidOCR（PaddleOCR 的 ONNX 离线版，
  模型随 pip 包分发，不联网）。持仓表实际只有 12px 字高，Windows 自带 OCR 在这个尺度下会把
  「黄金ETF」认成 `E±ETF`/`黄±ETF`、把 `518880` 认成 `S18880`，`×`/`±`/`亻` 混淆严重。
  系统 OCR 保留为兜底（未安装 RapidOCR 时自动回退）。
- **引擎可切换**：环境变量 `THSAPI_OCR_ENGINE=rapid|windows|auto`（默认 `auto`）。
- **价格小数点误识修复**：OCR 常把 `8.199` 读成 `8,199`，而原解析把逗号当千分位删掉，导致市价放大 1000 倍、
  盈亏算成天文数字。现在价格单元格出现"只有逗号没有点"时按小数点处理，并用
  「市值 ÷ 持股数」交叉校验，明显不一致时以校验值为准，随后重算盈亏与盈亏比。
- **按列校验 + 定点补读**：证券代码校验为 6 位数字、证券名称校验是否含可疑字符，
  只对可疑单元格二值化后按多组放大倍数重新识别（正常表格零额外开销）。
  补读放在"表格疑似残缺重拍"之后，避免重拍整表覆盖修复结果。
- **JSON 响应补 `charset=utf-8`**：`application/json` 不带 charset 时，部分客户端（如 Windows PowerShell 5.1）
  会按 Latin-1 解码，把 `黄金ETF` 显示成 `é»éETF` —— 这是客户端解码假象，现在服务端显式声明编码。
- **测试**：新增 2 个回归用例（OCR 小数丢失修复、名称乱码判定），`pytest` 从 20 → **22 passed**。
