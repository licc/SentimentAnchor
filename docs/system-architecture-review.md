# 情绪锚交易系统 · 架构审视

## 结论

当前系统已经不是简单的行情看板，而是具备：

- 行情与情绪计算
- T+0 ETF 与 T+1 股票两条策略线
- 策略库与 AI 生成
- 统一券商交易通道
- 买入风控与止损
- 执行审计与盈亏归因
- 交易事件因果链
- 单实例与 JSON 持久化

但它仍然是一个**单机、单进程、单操作者的实盘研究系统**，还不是成熟的机构级交易系统。

生产成熟度大致：

| 维度 | 评价 |
|---|---|
| 业务边界 | 中等，T0/T1 已分开，但底层命名仍有 ETF 历史包袱 |
| 交易安全 | 中等，有统一队列和风控，但缺持久化意图与启动对账 |
| 风控 | 基础，规则可用，但缺组合级、日内熔断和独立风控 |
| 策略 | 有模型和回测，但缺标准化编译器、OOS 和交易成本模型 |
| 可观测性 | 偏弱，主要靠页面和文件，缺指标、告警、追踪 |
| 测试 | 偏弱，有 smoke 脚本，缺单元/集成/契约测试 |
| 安全 | 基础，有可选 APP_TOKEN，但无 RBAC 和审计权限 |
| 部署 | 偏弱，单进程 + 文件存储 + 手工发布 |

总体判断：

> **可用的单操作者研究/小资金实盘原型，不是成熟的生产交易平台。**

---

## 二、做得好的地方

### 1. 交易通道统一

所有买入、卖出、撤单都经过：

```text
brokerCommand 唯一串行队列
→ brokerChannel 统一门面
→ etf-broker 唯一券商客户端队列
```

方向是对的。交易系统最怕多入口直连券商，这一点已经收敛。

### 2. T+0 与 T+1 分离

T+0 ETF 和 T+1 股票：

- 各自策略库
- 各自启用策略
- 各自执行规则
- 共用账户、资金、持仓和券商通道

这是正确的业务边界。

### 3. AI 只生成、不盘中执行

```text
AI 生成参数化策略
→ 服务端校验
→ 人工启用
→ 确定性代码执行
```

没有让 LLM 在 tick 中直接决定买卖，这是正确的。

### 4. 执行审计

已有：

- 订单编号
- 成交数量
- 多源确认
- 持仓变化
- 手续费
- 已实现盈亏
- 买卖原因
- 因果链

比“只记录买了还是卖了”成熟很多。

### 5. 未知委托处理

已有：

- 券商订单匹配
- 持仓差核对
- 梯度重试
- 共享快照
- 不重复下单

方向正确。

## 三、必须优先修的问题

## P0：交易安全

### 1. 缺少持久化订单意图 / Outbox

当前下单流程大致是：

```text
创建审计记录
→ 调用券商
→ 更新审计
```

如果进程在“券商已受理”和“审计已更新”之间崩溃，重启后只能靠对账恢复。

需要：

```text
order_intent 先落盘
→ 带幂等键发送
→ 收到结果后更新
→ 启动时先对账所有未完成 intent
```

核心原则：

> **先记录要做什么，再执行；不是执行后补记录。**

### 2. 自动执行重启后直接恢复（已改为默认暂停）

当前服务重启会恢复自动执行状态。实际运行中已经出现过重启后继续交易的情况。

需要：

```text
重启后默认进入 PAUSED / RECONCILING
→ 完成持仓、委托、审计对账
→ 人工确认恢复
→ 才允许新开仓
```

至少要有：

```text
resumeOnRestart: false
```

### 3. T+0 与 T+1 没有组合协调器

两个引擎可以同时运行，共用同一笔现金。

目前只有：

```text
指令串行
买入风控
```

但缺少：

```text
资金分配
账户总仓位协调
同一标的多策略冲突
谁先占用额度
```

需要增加 `TradingCoordinator`：

```text
账户级资金预算
策略级额度
单标的互斥
统一开仓许可
```

### 4. 风控不是独立进程

风控代码在交易进程内，交易进程崩溃时风控也停止。

成熟系统应把风控作为独立服务：

```text
策略 → 风控服务 → 券商网关
```

风控服务至少独立部署、独立心跳、独立 kill switch。

### 5. 缺少数据新鲜度和异常数据熔断

券商曾返回：

```text
518880 last_price = 202
market_value = 20200
pnl_pct = 2149%
```

实际价格约 8.2。

需要：

- 报价与持仓价格偏差检查
- 数据超过 N 秒未更新禁止开仓
- 账户市值与持仓市值交叉校验
- 异常数据触发暂停和告警

## P1：正确性与可观测性

### 6. 审计仍以 JSON 文件为主

当前：

```text
data/*.json
```

问题：

- 无事务
- 无索引
- 无并发写保护
- 难以查询历史
- 难以做资金流水和监管审计

建议：

```text
PostgreSQL / SQLite（单机）
订单表
成交表
持仓快照表
策略版本表
风控事件表
```

JSON 只保留导出和调试。

### 7. 缺少统一交易账本

现在有 journal、execution、risk events 多套记录，存在重复写入历史问题，已经做过去重，但根本问题是缺少唯一账本。

应有：

```text
OrderIntent
Order
Fill
PositionLot
CashLedger
StrategyRun
RiskDecision
```

所有页面从账本派生。

### 8. 没有指标和告警

需要至少：

```text
券商接口成功率 / 延迟
下单成功率 / 拒单率
未确认委托数量
自动执行状态
当日已实现盈亏
当日回撤
风控拦截次数
数据源延迟
```

以及告警：

```text
接口连续失败
未知委托超过 N 分钟
持仓与账户不一致
当日亏损超限
进程重启
```

### 9. 测试不足

当前有 smoke 脚本，但缺少：

- 单元测试
- 券商 mock
- 订单状态机测试
- 风控边界测试
- 断线/超时/重复回调测试
- 回测防止未来函数测试
- UI 关键流程测试

交易系统不能只靠手工点页面验证。

### 10. 回测不够严谨

当前 T+1 回测：

- 使用日线价格规则
- 不含历史情绪分数
- 不含涨跌停无法成交
- 不含停牌
- 不含滑点和冲击成本
- 没有样本外验证
- 没有参数过拟合检查

需要：

```text
训练集 / 验证集 / 样本外
手续费 + 滑点 + 涨跌停约束
基准对比
最大回撤和连续亏损
```

## P2：工程与产品标准化

### 11. 命名历史包袱

大量模块仍叫 `etf-*`，但已经被 T+1 股票复用：

```text
etf-broker
etf-execution
etf-write-confirm
etf-reconcile
etf-trade-lock
```

应逐步改成：

```text
broker-gateway
trade-execution
trade-confirm
trade-reconcile
trade-lock
```

### 12. API 不统一

当前：

```text
/api/etf/*
/api/quant/*
/api/risk/*
/api/strategies/*
```

缺：

- OpenAPI 规范
- 统一错误码
- 统一分页
- 统一幂等键
- API 版本

### 13. 前端组件过大

`EtfDesk.tsx`、`QuantDesk.tsx`、`RiskCenter.tsx` 都承载了较多业务。

建议拆成：

```text
AccountHeader
PositionTable
AutoStatusPanel
StrategyCard
TradeLedger
RiskDecisionTable
```

并建立统一 UI 组件：

```text
Card
SectionHeader
Metric
StatusBadge
Modal
Table
```

### 14. 安全与权限

当前只有可选 `APP_TOKEN`。

成熟系统需要：

```text
登录
RBAC
操作审计
敏感操作二次确认
API Token 轮换
密钥托管
```

至少实盘下单、自动启动、清仓必须有独立权限。

### 15. 部署与备份

当前单进程 + 文件。

需要：

```text
进程守护
健康检查
自动重启
数据备份
日志轮转
版本回滚
```

Dockerfile 已有，但还需要部署脚本、备份策略和恢复演练。

## 四、建议改造顺序

### 第一阶段：实盘安全

1. 订单意图持久化 + 幂等键
2. 启动强制对账
3. 重启默认暂停自动执行
4. 数据新鲜度和异常价格熔断
5. 独立 kill switch
6. T+0/T+1 资金协调器

### 第二阶段：账本与可观测性

1. SQLite/Postgres 交易账本
2. 统一订单/成交/持仓/现金流水
3. 指标和告警
4. 券商 mock 和状态机测试
5. CI 构建与回归

### 第三阶段：平台化

1. 拆分券商网关、风控、策略执行
2. 消息队列
3. 多用户/RBAC
4. OpenAPI
5. 前端设计系统
6. 策略样本外评价体系

---

## 五、不建议现在做的事

- 不要为了“AI 交易”让 LLM 直接在每个 tick 下单。
- 不要在没有订单账本前接更大资金。
- 不要先拆微服务再补对账。
- 不要把回测收益当成实盘能力。
- 不要用页面轮询替代后端告警。

---

## 六、最终判断

系统的基础方向是对的：

```text
统一券商通道
策略分层
风控前置
人工启用
执行审计
因果记录
```

但目前更像：

> **一个功能完整、正在实盘验证的单操作者交易工作台。**

距离成熟系统还差三件事：

1. **订单与资金的强一致账本**
2. **独立、可熔断的风控与运行监控**
3. **可重复的测试、回测和发布体系**

在这三件事完成前，不建议把它定义为“成熟生产交易系统”。
